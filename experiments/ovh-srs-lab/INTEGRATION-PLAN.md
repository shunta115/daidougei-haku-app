## 既存成果を壊さず統合する

- PR #87: HAKU DIRECT / CROWDの所有者限定試作。本人の事前許可、QR、配信交代、5視聴枠、緊急停止、試作用D1の原子的権限管理。**本番パフォーマー認証・本番投げ銭には未接続。**
- PR #88: SRSでのメディア配信ラボ。RTMP/HLSの負荷生成と、WHIPを使ったブラウザ側のワンタップ配信試作。**実SRSのWHIP→HLS・iPhone・500人性能は未検証。**
- どちらもDraftのまま維持し、mainや既存LiveKitの機能を上書きしない。

## 将来のユーザー操作

1. 本人はHAKU内で「LIVE開始」を押す（初回のみカメラ・マイク許可）。
2. 観客は本人の事前許可がある場合に限りQRを読み、「LIVE開始」を押す。
3. 撮影者は配信映像をSRSへ1本だけ送る。視聴者はHAKUのLIVE画面でHLSを視聴し、既存の投げ銭・フォロー導線を利用する。
4. 本人はいつでも停止・撮影者交代を指示できる。配信の中断や通信切断時には権限を失効させる。

## サーバー側で必要な実装（未着手）

- Supabase Authで本人/観客を検証し、パフォーマーの事前同意・停止状態を確認する。
- QRは公開の参加申請IDであり、SRSの公開配信権限を与えない。申請後にサーバーが**一度限り、短寿命、本人/観客/配信セッションに結合した配信許可**を発行する。
- 配信許可の取得・消費・更新・失効は、共有DBのトランザクションと一意制約で原子的に管理する。1パフォーマー1配信者の同時上限をサーバーで保証する。
- SRSのWHIP入口に認証ゲートを置き、権限を検証してから通す。**SRSのon_publishフックがWHIPに対して期待どおり動作するかは要実機検証。** 動作未確認のフックだけに依存しない。
- 配信キーやSRS管理用トークンをQR・ブラウザ・公開リポジトリへ渡さない。
- 停止・失効時にはSRS側の実メディア接続も切断できる仕組みを検証する。画面上だけの停止で済ませない。
- HLS視聴を非公開にする場合は、マニフェストだけでなくセグメントへのアクセスも制御する。公開LIVEなら視聴の無料・匿名条件を明示する。
- 既存Stripe投げ銭の受取先は常にパフォーマーIDとし、観客カメラマンには誤送金しない。
- 画像・音声の保存は初期段階で行わず、個人情報・第三者の撮影同意・通報・緊急停止を検証する。

## 500人視聴の受入基準（未達）

- 1パフォーマーあたり500人同時視聴、60分継続。別の配信を同時に何本運用するかは別途測定。
- 計画帯域: 800kbps映像+48kbps音声+15%余裕で約488Mbps、約219GB/時。
- SRSと日本のiPhone Safariで映像・音声・視聴開始時間・バッファリング・再接続・緊急停止を実測する。
- 実サーバー契約・外部負荷試験は料金・帯域・超過課金条件の個別承認後に実施する。
- 500人試験合格と、月額1万円以内での持続運用の確認は別々の合格条件とする。
