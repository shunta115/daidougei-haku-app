## 優先実装 (縦断フローごとに完結)
### P0-1 Stripe Connect
1. パフォーマーMy Pageから「売上を受け取る」1 CTA。
2. 未開始/入力途中/審査中/追加情報必要/送金可能/制限中をAPIの実状態で区別。
3. Stripe Hosted Onboardingの再開と期限切れリンク更新。アカウント重複作成禁止。
4. テスト環境で初回・中断・再開・審査状態をE2E。
5. 本番で既存の台帳とStripe実績をREAD ONLY照合。差額・未照合は止める。Transfer有効化は別承認。

### P0-2 投げ銭と分配
1. 金額確認→Stripe Checkout→Webhook確定→台帳→パフォーマー売上表示。
2. 決済の冪等性、Webhook再送、返金、手数料、残高、Transfer、Payoutを区別。
3. 金額保存不変条件と端数テスト。支払完了と銀行入金を同一ステータスにしない。
4. 本番資金移動は監査と明示承認まで停止。

### P0-3 LIVE
1. 配信準備→配信開始→ファン一覧→視聴→コメント→終了を2端末で通す。
2. Test Performerは非公開維持、許可済みs.sのみ表示・視聴。RLS・token発行・Realtime・MAP・通知も同じ権限に統一。
3. カメラ・マイク拒否時の回復UI、回線切断再接続、音声/映像連続性を実機検証。
4. 予約と開始通知はフラグ・DB migration・送信経路の稼働をそれぞれ検証。

### P0-4 出演予定と通知
1. パフォーマーが日時/場所/公開範囲を登録。
2. フォロワーが予定を保存し、許諾済み通知チャネルへ配信。
3. 前日・開始前・開始時刻の重複排除/時刻帯/取消/変更をテスト。
4. 通知タップ→正しい出演予定/地図/LIVEへ遷移。通知権限拒否時はアプリ内通知で代替。

## 情報設計
ファン: 「見つける」「LIVE」「予定」「マイページ」の4タブ。トップの第一画面は近くの開催予定または視聴可能なLIVEを主CTAにする。情報がないときは地域変更・フォロー提案・次回予定を表示。
パフォーマー: 「配信する」「予定を登録」「売上」「マイページ」。未完了Stripe登録は「売上を受け取る」で明確に表示する。
主催者/管理者の専門機能は通常ファンの導線に混ぜない。

## 行動科学・HCIを実装へ落とす
- 認知負荷: 1画面1主目的、主要CTAは1つ。段階的開示で初回入力を短くする。
- Hick-Hyman: 無関係な選択肢を折りたたむ。初回ファンに管理者/主催者機能を見せない。
- Fitts: 親指が届く下部に44px以上のタップ領域、誤操作しやすい危険操作は距離を取る。
- Nielsenの可視性: 送金「準備中/実行中/完了/要確認」を正確に表示。成功を先に宣言しない。
- 自己決定理論: フォロー/応援は本人の意思。通知許可と投げ銭は任意、罪悪感・偽の緊急性を使わない。
- アクセシビリティ: WCAG 2.2 AAを目標、文字コントラスト、VoiceOverラベル、動きの低減、キーボード操作、エラー修正案内。
- パフォーマンス: 低速回線・低性能端末でも主要CTAと現在状態を早く表示。ローディング/空状態/エラー状態を設計。
